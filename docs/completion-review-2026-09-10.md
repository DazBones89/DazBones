# DazBones 完成に向けたコードレビュー

確認日：2026-09-10

## 確認範囲と結論

Java 48ファイル、HTMLテンプレート28ファイル、アプリケーション設定、Gradle設定、既存仕様書・開発資料を確認した。画面とCRUDの土台はあるが、認証の抜け道、カレンダーの組み込み不備、未実装のURL、集計の不整合があり、公開前に主要動線を完成させる必要がある。

本資料は静的レビュー。localhost:8080への接続は拒否されたため、現時点のブラウザ表示・実DBでの再現、更新操作、ビルド・自動テストは未実施。実DBの制約や外部の運用設定は未確認。アプリケーションコードは変更していない。

優先度は「最優先＝公開前に修正」「高＝主要機能の完成に必要」「中＝運用・品質改善」。既存仕様書のチェック済み表示と実装状況は一致していないため、完了判定は実コードを基準とした。

## 4. 中：エラー処理・使いやすさ・保守

- **HTTP応答を正す**：`return "error/404"` や共通例外ハンドラーはHTTPステータスを設定していない。画面上404/500でも200になり得る。APIにはHTMLではなく適切なステータスとJSONエラーを返す。
- **内部エラーを公開しない**：`GlobalExceptionHandler` と `error/500.html` が例外の生メッセージを表示する。サーバーログに詳細を記録し、画面は一般向けメッセージと問い合わせ用識別子にする。現ハンドラーにはログ出力もない。
- **認可を共通化する**：各ControllerでisAdmin/canManageが重複し、`AuthUtil`が未使用。URLごとの権限表と共通処理を作り、セッション切れ時の動作を揃える。60分タイムアウト設定自体は存在する。
- **回答者切り替え時にフォームを再取得する**：surveyの名前セレクトに変更時の再読み込みがない。他の人の回答を表示したまま名前だけ変えて保存し得る。未回答時は回答値も初期化する。代理回答を許すかは仕様として決める。
- **通信失敗を表示する**：surveyのfetchにHTTPステータス確認・catch・保存中の二重送信防止がない。セッション切れ・ネットワーク失敗から復帰できるUIが必要。
- **集計クエリをまとめる**：アンケートは日ごとに回答者取得・祝日確認・複数countを実行し、eventsとday-typesの両方で繰り返す。日付範囲でまとめて取得・集計する。部費も選手ごとの取得を減らす。
- **同時編集を扱う**：イベント作成・回答更新・祝日登録の「検索してから保存」に競合時の処理がない。DB制約の確認、トランザクション、必要箇所の楽観ロック等を整備する。
- **代替画像を用意する**：`/images/default-group-photo.jpg` は参照されるがファイルがない。集合写真がない環境では代替も表示できない。トップ写真欄は同じ集合写真4枚の仮表示。
- **PC・モバイルUIを仕上げる**：共通レイアウトは最大480px固定。既存仕様のPC表示切替・ダークモード・設定保持・問い合わせ付きフッターは未実装。下部ナビはどのページでもホームが強調される。
- **キーボード操作を整える**：メニューの開閉状態、モーダルのフォーカス移動・復帰・Escape対応、入力ラベルと入力欄の関連付けを確認する。
- **CSS配信を整える**：共通CSSはTailwindのブラウザ実行CDNに依存。公開用の固定したCSS生成・配信手順を用意し、FullCalendarを含め必要資産の読込成功を確認する。
- **公開前の表示確認**：タイトル・説明文・SNS共有用情報、スマホの長いメニューと固定ナビの重なり、空データ・長文・画像欠損をチェックする。

## 6. 公開・開発環境の整備

- `application.properties` と `application.yml` にDB設定等が重複。YAMLの `app.spring.jpa...` は通常のJPA設定と異なる階層。設定を整理し、開発/テスト/本番で接続先・ログ・保存先を分ける。
- `ddl-auto=none` だが、リポジトリ内にDB作成・更新用SQLやマイグレーションがない。新環境を再現できるよう、現DBとの差分と外部キー・一意制約・索引を確認して管理する。
- 本番配置の定義、DB接続・秘密値・ポート・永続画像保存先の手順がない。ローカル相対パスへの画像保存と固定DB接続を本番運用に合わせる。
- バックアップ・復元手順、自動バックアップスクリプト、監視・障害調査手順はリポジトリ内にない。既存仕様の週1/5世代・画像変更時バックアップを採用するか整理する。外部で運用済みかは未確認。
- `uploads/images/group-photo.jpg` はGit追跡対象。今後のアップロード画像をリポジトリで扱うか、永続ストレージとバックアップで扱うかを決める。
- `/testlinks` は「本番では非表示」の説明のみで、Profile制限がない。本番では無効にする。
- `src/test` にテストがなく、CI設定もない。まず認証・権限、テンプレート描画、主要CRUD、公開日時、削除後の集計、アップロード失敗を回帰テスト対象にする。
- Java/Spring Boot/Gradle/フロント資産の更新方針と依存関係チェックを整える。最新バージョンや既知脆弱性の調査は今回の対象外。
- READMEはタイトルのみ。DBの用意、必要環境変数、起動・終了・バックアップ・デプロイを記載する。`docs/player-crud-spec.md` 等の旧 `/player/add`・`/player/edit/{id}` を実装の `/players/add`・`/players/{id}/edit` に合わせる。

## 7. 推奨する作業順序と完了条件

1. **認証と公開制御**：A1〜A4を修正。URL直アクセスではログインできず、権限外更新・CSRF・公開前閲覧を拒否する。
2. **主要画面を動かす**：B1〜B8を修正。データがある状態で選手一覧・編集、両カレンダー、予定CRUD、回答者管理、写真ページが使える。
3. **保存・集計を正す**：C1〜C11を修正。削除・復元・不正入力・画像保存失敗・CSV途中エラーでもデータと表示が一致する。
4. **完成範囲を満たす**：採用する外部連携・管理機能・履歴・PC表示を実装し、仮表示とリンク切れをなくす。
5. **公開準備**：新環境でDBとサイトを再現し、画像を永続保存でき、バックアップから復元できる。権限別・スマホ/PCで主要動線を確認する。

最初の開発単位は「認証修正 → 共通レイアウト修正 → 活動予定API/CRUD → 選手取得修正 → 回答者管理の接続」を推奨する。ここまで進めると、その後の機能を実画面で確認しながら完成させやすくなる。
